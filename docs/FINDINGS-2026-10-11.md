## c1 — Issue 1: "library only shows up to N, doesn't paginate, might be by add date"

### What is established and what is not

**Established (evidence above):**

1. The failures are exactly coextensive with the toggle being on: 22/22 songs failed with it on,
   0 failed with it off, same phone, same server, same songs, within one minute of each other.
2. The only playback-path behaviour gated on `autoMixEnabled` for the current item is the custom
   scheme + `CachingResourceLoaderDelegate` in `makePlaybackAsset`. With the toggle off the asset
   is the plain `AVURLAsset` it always was (`PlaybackEngine.swift:2400-2407`).
3. The items failed immediately on every candidate, so the loader-fed item is being rejected by
   AVFoundation at load time, not timing out.
4. The two transcoded fallbacks cannot work through this loader even in principle: Navidrome's
   uncached transcode branch sends `Accept-Ranges: none`, ignores `Range`, and sets no
   `Content-Length` unless `estimateContentLength=true` is passed (it is not — `NavidromeClient.swift:601-609`),
   so `totalLength(from:)` (`CachingResourceLoaderDelegate.swift:263-271`) returns nil,
   `info.contentLength` is never set (`:195`) while `info.isByteRangeAccessSupported = true` is
   asserted (`:194`). The fallbacks therefore add nothing; the raw candidate is the one that has
   to work.

**Not pinned down, and I will not guess:** *why* AVFoundation rejects the raw candidate through
the loader. The server returned the raw bytes (every raw line is `transcoding=false`, 2-3 ranged
requests per attempt, no error status), so the rejection is on the device side and the server log
cannot see it. Candidates that fit the symptoms but are unverified here: the content-information
handshake on the `vellumcache://` scheme (`CachingResourceLoaderDelegate.swift:124-135`,
`:185-205`) on the iOS version on his phone; the `UTType(mimeType:)` → `contentType` mapping for
`audio/flac` and `audio/mpeg`; the `AVURLAssetOutOfBandMIMETypeKey` option being nil for raw URLs
(no `format` query); or `TapPlayerItem.make` awaiting tracks on a custom-scheme asset.

**What would settle it (one of):**

- The device log for one failed song with the toggle on: `PlaybackEngine.autoMixLogger`
  (`os.Logger`, `.notice`, public — Console.app or `log collect` on the phone) prints
  "caching loader attached to the playing stream" then the failure; and `AVPlayerItem.error` /
  `item.errorLog()` for that item, which `PlaybackFailurePolicy.classify` sees at

## c3 — Issue 3: playlist description length limit, and "can't edit the playlist"

### The actual limit (read, not written)

- **Navidrome source, v0.61.2:** `server/subsonic/playlists.go` reads `comment := p.StringPtr("comment")`
  and passes it to `api.playlists.Update(...)`; `core/playlists/playlists.go` `updateMetadata`
  does `if comment != nil { pls.Comment = *comment }`; `persistence/playlist_repository.go` `Put`
  stores it. **No length validation on comment or name in any of the three layers.** The web UI
  (`ui/src/playlist/PlaylistEdit.jsx`) renders `comment` as a multiline `TextInput` with no
  `maxLength` and no `validate`.
- **Schema:** `playlist.comment varchar(255) default '' not null` — but SQLite does not enforce
  `varchar(N)`; the only hard limit is SQLite's `SQLITE_MAX_LENGTH` (1,000,000,000 bytes).
- **Existing data proves it:** the longest `playlist.comment` on his server is **9,667 characters**
  (`__lyra_e05723b73736`, owned by `ethan`), and Vellum's own magic playlist
  `__vellum_ee68fe4b9a8a` carries a 1,860-character JSON comment, both written through Subsonic
  `updatePlaylist` by Vellum (`NavidromeClient.swift:1639-1642 setPlaylistComment`). 4 of 65
  playlists have a non-empty comment.

So: **there is no practical character limit on a Navidrome playlist description.**

## Issue 1 — the catalog and the Recently Added grid (c1)

**Structural cause:** `albums(limit:)` was one `getAlbumList2` page, and `limit` was a page size.

- `Backends/AlbumCatalogPager.swift` (new): `fetchAll(pageSize:maxItems:fetchPage:)` walks by
  offset until a short or empty page, sizing the last page to the ceiling. Pure; the loop is the
  tested unit. Tests (`AlbumCatalogPagerTests`): exact multiple of the page size (1000 rows →
  offsets 0/500/1000, the third page empty), short last page (1200 → three requests, no fourth),
  empty library (one request, no rows), ceiling (700 → sizes 500 + 200), a thrown page propagates.
- `NavidromeClient.albums(limit:)` walks `getAlbumList2?type=alphabeticalByName` through the pager;
  `JellyfinMusicClient.albums(limit:)` walks `Items` with `StartIndex` (new parameter on
  `fetchAlbumSummaries`). `AppModel.defaultLibraryAlbumFetchLimit` is now a **ceiling of 50,000**,
  not a page size. On his server that is 27 requests of 500 and 13,300 albums in memory.
- **Recently Added grid: incremental loading** (my call; stated here). `LibraryView` keeps the
  first 60 as before and shows a stock bordered **"Show More (N left)"** button under the grid,
  growing by 60 per tap (`Library/LibraryRecentPaging.swift`, `nextLimit(current:total:)`). #61
  "party" is one tap away. Tests (`LibraryRecentPagingTests`): 90 → 90, 400 → 120 → 180, nothing
  more at the end, page size pinned at 60.
- Not changed: Home's Recently Added **shelf** (`type=newest&size=60`) is a shelf, not a list;
  Settings' statistics walker was already paged.
- Risk to watch on the device: `libraryAlbums` holds the whole catalog now. `rebuildLibraryAlbumIndex`,
  `LibraryAlbumReleaseIndex` and the snapshot write run over 13,300 rows instead of 500 (the
  PerfLog lines `refreshLibraryAlbums.fetched` and `rebuildLibraryAlbumIndex.albumsOnly` carry the
  counts and timings). If that is slow, the next step is to page the index too — not to cap the
  fetch again.

## Issue 2 — the caching loader (c2)

**Structural cause:** every network candidate — raw, mp3 fallback, aac fallback — was built on
the custom scheme whenever the toggle was on, and a loader rejection meant the song did not play.

**The rule, now in one place (`Playback/PlaybackCandidateLadder.swift`):**

1. The loader may be attached only while AutoMix is on, only to a progressive http(s) stream
   that is not internet radio, not HLS, and **not a transcode**:
   `CachingResourceLoaderDelegate.servesByteRanges(url)` is false for any URL carrying
   `format≠raw`, `maxBitRate`, `audioBitRate`, `audioCodec`, `audioSampleRate`, `maxAudioBitDepth`,
   `transcodingContainer`, `transcodingProtocol`, `estimateContentLength`, or (Jellyfin)
   `static≠true`. Navidrome serves those with `Accept-Ranges: none` and no `Content-Length`.
2. Only the **first** eligible URL gets a loader attempt, and it is immediately followed by the
   **same URL as a plain `AVURLAsset`**. Transcoded fallbacks are always plain.
3. With the toggle off the ladder is exactly one plain attempt per URL — unchanged.

So the ladder for his default (Original) format is `raw via loader → raw plain → mp3 plain → aac
plain`; whatever rejects the loader-fed item, the song plays on the second attempt and only that
song's first boundary loses its blend (the next track is fetched by the prefetcher as before).
`PlaybackEngine.shouldAttachCachingLoader` now delegates to the ladder's `mayUseLoader`, so the
gate and the ladder cannot disagree. Tests (`PlaybackCandidateLadderTests`): the rule on raw /
explicit raw / Jellyfin static (true) and mp3 / aac / bitrate-capped / Jellyfin transcode (false);
the gate agrees; the three ladders above plus a transcoded primary (loader only reaches the raw
fallback), a local file first, radio, headers preserved.

**The real reason, logged:** `PlaybackEngine.logCandidateFailure` writes one line per rejected
